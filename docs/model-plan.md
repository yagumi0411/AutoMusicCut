# 模型方案可行性讨论（暂缓实施）

> 记录日期：2026-09-14
>
> 状态：**设计方案，暂不实施**。当前版本仍以 `amc/detect.py` 的手工特征方案为准。
> 本文记录一次关于"改用学习模型"的完整讨论，供后续拓展时参考，不构成实施承诺。

## 1. 背景：现方案在真实数据上的表现

在真实样品上跑完 `tests/calibrate.py` 后得到的关键数据：

| 素材类型 | 窗得分中位数 |
| --- | --- |
| 唱歌片段 | 0.95 |
| 杂谈片段 | 0.87 |

两个分布**几乎完全重叠**。`WIN_SCORE_THRESH = 0.6` 这个阈值下杂谈窗会大量越线，
任何阈值取值都会同时产生大量误报和漏报。也就是说，手工特征方案在当前内容上
基本不可用，这不是"阈值没调好"的问题。

## 2. 为什么会失效

两个原因都是结构性的，调参解决不了：

### 2.1 中文是声调语言

普通话每个音节内部音高本身就稳定（一声平、四声降都有平稳段），音节时长约
0.15~0.25s。而当前的核心判据是"音高稳定 = 唱歌"，`STABLE_RUN_SEC = 0.2`
这个阈值正好卡在普通话音节的尺度上——**杂谈在特征空间里长得就像唱歌**。

这是 F0 类特征在中文内容上的固有弱点。作为对照：日文是音高重音语言、法文是
非声调语言，音节内音高都比中文平得多，同样的判据在日文/法文上反而更可靠。
**中文是这几类内容里最难的。**

### 2.2 demucs 分离不干净

杂谈段的 BGM 会残留在人声轨里，残留的谐波成分在 pyin 看来就是稳定的周期性
内容，进一步抬高杂谈的"唱歌分"。

### 2.3 模型能补的是什么

模型的收益上限由此确定：它可以吃到手工特征根本覆盖不到的信息——

- 音节速率与发声段时长分布
- 共振峰轨迹
- 谐噪比（HNR）
- 频谱通量在节拍尺度上的周期性

这些是区分"说/唱"最有效的判据，而且**不依赖音高稳定性**，正好绕开中文的坑。

## 3. 模型方案的优势

- **判别力**：唯一能突破上述天花板的手段。目标可定为段级 F1 ≥ 0.9。
- **可以彻底砍掉 demucs 与 pyin**：直接在原始混音上训一个 log-mel 分类器，让它
  自己学"带 BGM 的歌声"长什么样。连带收益是推理从"分离 + 逐段 pyin"的十几分钟
  降到几十秒，对 2~4 小时录播是数量级差别。
- **边界更准**：帧/窗级概率天然给出软边界，比能量 VAD 的粗边界紧，人工修边界的
  工作量下降。
- **真正改善的是人力指标**：收益不是"全自动"，而是每小时视频的人工试听时长。
  现方案候选清单约等于全片，模型能把候选压缩到接近真实唱歌段，人工从"扫一遍"
  变成"确认 + 填歌名"。

## 4. 模型方案的成本与劣势

- **主要成本在数据清洗，不在训练**。训练本身不是瓶颈，整理标签才是。
- **训练管线要从零搭**：切窗、划分、增强、训练、早停、概率到区间的后处理。
- **黑盒**：出错只能靠错误分析（听误判片段）迭代，不如阈值直观。
- **泛化差**：单一主播/麦克风/房间训出的模型换人必崩。作为个人自用无妨，但本
  项目是公开发布的工具，模型不能作为通用能力发布（见 §8 的发布形态建议）。

## 5. 数据方案：多主播

设想的数据规模：3 个主播 × 各 20 小时杂谈 + 各 30 首以上歌切。

### 5.1 能解决什么

先纠正一个说法：**难点不是"音色"，是"说话基频基线"和"语速/唱法风格"。**

音色（共振峰、声道长度）对区分说/唱几乎没用——同一个人说话和唱歌音色是一样的。
真正随人变化的是：

- **说话基频基线**：男女差接近一个八度。绝对音高阈值必然失效。
- **语速**：有人 5 音节/秒，有人 7 音节/秒。绝对"音节速率阈值"同样失效。
- **唱法风格**：有人气声轻唱，有人真声硬顶。

多个主播能提供这三项的变化幅度，**强制**模型去学相对特征（如相对于该主播说话段
中位 F0 的音高）而不是死记绝对数值。这是最大的收益。附带好处是不同主播大概率是
不同麦克风/房间/编码链路，等于免费的域增强。

### 5.2 解决不了什么

- 3 个说话人在说话人空间里仍然极其稀疏。第 4 个主播如果语速或唱法与这三人差异
  大，仍会掉点。
- 更隐蔽的风险：如果三人都是中文主播、都是同类直播风格，模型学到的是"这一类
  直播间的说话方式"，而不是"人类说话"。

### 5.3 必须做的验证：留一说话人交叉验证（LOSO）

3 个主播正好做 3 折，每折用 2 人训练、1 人测试。这是唯一能给出真实跨主播数字的
方法。**用"同主播随机划分片段"得到的指标没有意义，会高估 10~20 个点。**

### 5.4 一个反直觉的建议

**说话人多样性比单说话人数据量更重要。** 如果能用 20 小时中的一部分去换更多主播
（比如 10 个主播 × 3 小时杂谈 + 10 首歌），跨主播表现通常比 3 × 20 小时更好。
最优是"几个深 + 若干个浅"的混合。

### 5.5 数据量换算

60 小时杂谈 + 约 6~12 小时唱歌，按 10s 窗 / 5s 跳切分：

- 负样本窗约 43200 个，正样本窗约 5760 个
- 正负比约 **1:7.5**，比单一主播场景更不平衡

训练时要用类别加权或平衡采样，评估时**不要看 accuracy**。

## 6. 数据方案：多语言（日文、法文）

目标内容可能不止中文，还会有日文歌、法文歌。结论：**能覆盖，但有一个必须遵守的
规则。**

### 6.1 核心规则

**正样本出现哪些语言，负样本就必须覆盖哪些语言。**

这是最容易踩的坑：如果正样本里加了日文歌、法文歌，而负样本全是中文杂谈，模型会
学成"**非中文的语音 = 唱歌**"。结果是日文访谈、法文旁白会被判成歌。

所以负样本要补多语言语音，成本很低——日文动画对白、日本广播、法文播客都能拿到，
每语言几小时就够把分布撑开。训练数据里建议按语言打标签，方便错误分析。

### 6.2 语言本身不是主要障碍

如 §2.1 所述，中文是这几类里最难的一档。真正需要重建的判据（音符时长、持续发声
段、颤音、节奏规整度）与语言无关。

### 6.3 混音风格差异可能比语言影响更大

J-pop / anime cover 伴奏通常压得很响、有侧链压缩和电子处理；法式香颂可能只是人声
加一把吉他，信噪比完全不同。如果模型直接在混音上跑，必须见过大的伴奏强度跨度。

这正好由 §7.2 的增强策略直接覆盖——**"干净歌切 + 伴奏按不同信噪比混回去"这一招
同时解决语言、流派、混音三件事。**

### 6.4 预训练 backbone 选型

若走微调路线，优先选多语言自监督模型（XLS-R / MMS 这类，训练语料覆盖上百种语言），
它们的表征对语言基本不敏感。避免用英文语料为主的模型，否则跨语言时相当于换个域。

### 6.5 不需要做的事

**不要加语言识别模块，也不要把语言 ID 作为模型输入。** 语言是干扰项不是有效特征，
靠数据覆盖解决就够了。

## 7. 数据准备中的三个坑

### 7.1 同场次泄漏

如果歌切片段正好剪自杂谈素材，必须**按场次划分**训练/验证/测试，不能按片段随机
划分，否则指标虚高到没有意义。

### 7.2 正负样本的分布不对等

歌切是人工剪干净的完整歌曲，而部署时歌声嵌在连续流里，前后有串场、淡入淡出、增益
变化。模型在"歌中间"的窗上学到的东西是对的，但边界附近会退化。

缓解办法：**用 demucs 分出伴奏轨，与干净歌切按不同信噪比混回去**，造出接近直播流
的样本再做增强。其他有效增强：变调（±2~3 半音）、共振峰偏移、变速、加噪加混响。

### 7.3 负样本是弱标签

"杂谈素材"是假定不含唱歌的。里面若混有未标注的歌声，就成了噪声标签。

缓解办法：先跑一遍现有检测器，把得分最高的"杂谈"窗挑出来人工听一遍，做一轮
**硬负样本挖掘**。

## 8. 建议的落地路线（分阶段）

1. **先花 1~2 天验证一个便宜的中间方案**：在现有管线里加"音节速率 / 发声段时长
   分布"特征，并把 `STABLE_RUN_SEC` 从 0.2s 提到 0.4~0.5s，看真实数据上的分离度
   能否改善。这是判断"到底需不需要模型"的最快手段，也可能直接解决问题。
2. **不够就上模型，但先用小模型**：对二分类任务，一个 5~10M 参数的 mel 谱 CNN
   就够，每轮训练几分钟、迭代快。不要一上来就微调 AST / PANNs 这类 8000 万参数
   以上的预训练模型——不是不行，是迭代代价高，且瓶颈在标签不在模型容量。小模型
   不够时再升级到预训练路线。
3. **留出测试集不动**：用那份带人工时间戳真值的完整录播作为唯一的留出测试集，
   指标用**段级**（与真值段 IoU > 0.5 记为命中）而非窗级准确率——窗级会严重高估
   实际体验。
4. **按主播 + 按语言分层做错误分析**，分开报告指标。混在一起的平均值会掩盖
   "某个语言或某个主播完全失效"这类问题。
5. **发布形态加一个"标定模式"**：这是一个开源工具，不能发布针对特定主播训出的
   模型。可行形态是工具提供特征基线 + 训练脚本，让用户用自己的素材微调；新主播
   只需人工标注 5~10 分钟（约 30~60 个窗）就能校准决策阈值。这比重新微调便宜
   两个数量级，通常能把跨主播的 F1 拉回接近同主播水平。

## 9. 模型不解决什么

**不解决歌名识别。** 音频指纹只能匹配原唱，翻唱匹配不了。所以"半自动 + 人工填
歌名"的流程框架不变，模型改善的只是候选区间质量。这一条无论走哪条路都不会变。
